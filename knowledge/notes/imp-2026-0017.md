# imp-2026-0017 — taurushq-io/frost-ed25519 (Go, pre-RFC)

## Honest framing

This implementation is NOT equivalent to "ZKSecurity frost Go
reference" mentioned in the original scout report. **ZKSecurity does
not host a FROST repository** (verified by enumerating all
`zksecurity/*` repos via the GitHub API on 2026-08-31).

The closest Go FROST candidate is `taurushq-io/frost-ed25519`, originally
`github.com/taurusgroup/frost-ed25519` (renamed when Taurus Group became
Taurus HQ). It implements the *paper version* of FROST
(Komlo et al. ePrint 2020/852, "single-round" variant), which is the
PROTOCOL PREDECESSOR to RFC 9591 (RFC 9591 was finalized June 2024; this
repo was last updated 2021-07-07).

**This repo is therefore not strictly RFC 9591-conformant** and is
included in the cohort as a:

1. **Go-language representative** — ensures cross-impl diversity.
2. **Historical baseline** — characterizes the pre-IETF FROST state.
3. **Negative control** — any RFC 9591-specific feature (binding-factor
   domain separation, identifier-as-scalar, etc.) should produce
   known, expected divergences here, NOT false positives.

## Internal implementation choices (audit-relevant)

- **Binding factor hash**: SHA-512 per Ed25519, but preimage layout is
  per the FROST paper §5.1 (`message || pk_group || commitment_list || id`),
  NOT per RFC 9591 §4.2 (`pk_group || H4(msg) || H5(commitments) ||
  additional_prefix || identifier_serialize`).
- **Challenge hash**: SHA-512 per RFC 8032 PureEdDSA. Identical to RFC 9591.
- **Hash-to-scalar**: SHA-512 reduced mod q; no RFC 9380 `hash_to_field`.
- **Lagrange basis**: naive product `lambda_i = prod_{j != i} j / (j - i)`
  evaluated at 0 (paper §5.2). No barycentric shortcut.
- **Participant index encoding**: `uint16` (`party.ID`), serialized as
  2-byte big-endian in transport messages. **NOT** a scalar field element.
  This is a known divergence from RFC 9591 §4.2.
- **Curve**: Edwards 25519 via Ristretto (cofactorless group), encoded as
  Ed25519-compatible bytes via `BytesEd25519()` cofactor-removal trick.

## Audit-role notes

For msn-2026-0013, this repo is a NEGATIVE control. The expected
verdict matrix for this implementation is:

- **Round 1 commitments**: byte-different from RFC 9591 §4.2 (no H4/H5
  domain separation, but the commitments themselves may coincidentally
  match if the inputs to the polynomial commitment are the same).
- **Binding factor `rho_i`**: byte-different (different preimage
  structure).
- **Challenge `e`**: byte-same (both use SHA-512 of `R || pk || msg`).
- **Aggregate signature**: byte-different (because binding factor differs).
- **Aggregate verification**: byte-different; the taurushq-io aggregate
  will verify under the paper-version group commitment but NOT under
  the RFC 9591 group commitment structure.

These divergences are NOT bugs in either implementation; they are the
correct behavior of two protocol variants. The mission acceptance
criteria should treat this implementation's divergence as
"conformance-equivalent, expected divergence at binding-factor preimage"
rather than "byte-exact match" or "byte-exact divergence".
