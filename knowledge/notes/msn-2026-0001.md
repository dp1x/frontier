# msn-2026-0001 — final notes

## The question

Which public ML-KEM implementations enforce the FIPS 203 §7.2 encapsulation-key
checks (type check `len(ek) == 384k+32`; modulus check
`ByteEncode12(ByteDecode12(ek[0:384k])) == ek[0:384k]`), **where** in the API
stack, and is omission permissible given the standard's placement language and
SP 800-227?

## Answer (verified: [[fnd-2026-0001]])

Three placements exist in the wild:

| Implementation | Pinned version | Check placement | Malformed ek behavior |
|---|---|---|---|
| PQClean clean | master `0586a824` (archived) | **nowhere** — API cannot signal | accepts all length-valid inputs |
| liboqs / mlkem-native v1.2.0 | `0.16.0` @ `5a1a854b` | **Encaps-time** (`mlk_kem_check_pk`) | rejects all non-canonical |
| OpenSSL | `3.5.7` @ `8cf17aae` | import-time | rejects both classes |
| Go stdlib crypto/mlkem | go1.26.4 | import-time, classified errors | rejects both classes |
| RustCrypto ml-kem | crate 0.3.2 | import-time | rejects both classes |
| .NET MLKem | runtime 10.0.11 (CNG) | import-time, classified errors | rejects both classes |

Omission-at-encaps is not a violation of §7.2's placement language ("checking…
need not be performed by the encapsulating party, nor with every execution"),
though [[spc-2026-0001]] §3.3 admits a stricter reading under which shipping a
check-free ingestion surface without documenting caller obligations is at
minimum deficient — and no SP 800-227 assurance case covers deployments that
feed such surfaces wire-supplied keys.

## The hazard shape (executed, controlled)

The naive "silent divergent secret" channel is **structurally impossible**:
`(K,r) ← G(m‖H(ek))` derives encryption randomness from raw key bytes
([[hyp-2026-0007]] rejected). What accepting libraries actually create is a
**one-sided key-establishment failure**: sender gets rc=0 success, honest peer's
implicit-rejection decapsulation yields an unrelated secret — invisible to
component-level conformance tests (inference from shipped coverage), visible at
application level ([[hyp-2026-0008]], controls in [[obs-2026-0009]]).

## Process lessons preserved

- Demanding positive controls exposed a swapped decap ABI that plausible-looking
  output had hidden.
- Independent reproduction caught two real defects before evidence was trusted
  (uncommitted harnesses; fix-introduced quoting regression).
- Runtime-vs-compiled version logging caught an OpenSSL header/library skew on
  the first CI attempt.
- Lineage correction mattered: PQClean and liboqs share one upstream; Go/Rust/
  .NET provided the actual independence.
