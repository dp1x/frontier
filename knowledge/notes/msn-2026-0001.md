# msn-2026-0001 — working notes

## The question

Which public ML-KEM implementations enforce the FIPS 203 §7.2 encapsulation-key
checks (type: `len(ek) == 384k+32`; modulus: `ByteEncode12(ByteDecode12(
ek[0:384k])) == ek[0:384k]`), **where** in the API stack, and is omission
permissible given the standard's placement language and SP 800-227?

## Spec ground truth (verified against committed PDF + NIST primary sources)

- [[spc-2026-0001]] — checks mandatory-on-the-module as a precondition;
  placement/frequency explicitly flexible; assurance-by-other-means per
  SP 800-227 §3.2 (final, 2025-09-18): three cases (internal generation +
  tamper-proof storage / check-once + storage / TTP import).
- Errata watch resolved 2026-08-24: no published or potential erratum touches
  §7.2/§7.3/§4.2.1.
- Eq. 7.1 constrains ONLY `ek[0:384k]`; the trailing 32-byte ρ seed is
  unconstrained by design.

## What surprised us

- **Congruent-plant refutation ([[hyp-2026-0007]])**: planting an overflow that
  decodes back to the original coefficient does NOT produce identical
  ciphertexts — `(K,r) ← G(m‖H(ek))` derives encryption randomness from raw key
  bytes, so any byte change re-randomizes the ciphertext, and the honest peer's
  implicit-rejection check fails the connection closed. The "silent divergent
  secret" channel is structurally impossible under FIPS 203's Encaps; the real
  hazard shape of accepting libraries is a *one-sided establishment failure*
  (sender believes a key was established; peer derives an implicit-rejection
  secret) — invisible to component self-tests, visible at application level.
- **Lineage correction**: PQClean and liboqs≥0.13 both descend from the
  pq-crystals C reference (mlkem-native is a fork); the candidate set needed
  Go/Rust/.NET for genuine independence.
