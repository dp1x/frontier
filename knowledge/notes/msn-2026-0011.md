# msn-2026-0011 — SSH hybrid KEX protocol-layer FIPS 203 s7.2 audit — Stage C

## 1. Mission summary

**Objective:** Determine whether OpenSSH portable ssh *client* catches
non-canonical C_PK2 via FIPS-conformant decapsulation of server S_REPLY.

**Result:** OpenSSH portable master HEAD commit 0ef0f5a8 ssh client is
**structurally symmetric** to the server in being length-only lenient on
its KEM half input (S_REPLY for client, C_INIT for server).

**Critical distinction:** on the client side this is **NOT a FIPS 203 s7.2
modulus check concern** because s7.2 is defined for encapsulation keys
(ek), not ciphertexts. The client's FIPS 203 surface is s7.3 (decapsulation
input checks via implicit rejection), delegated to crypto_kem_mlkem768_dec.

**Structural safety net:** the SSH exchange-hash signature verification on
H = hash(... || K_PQ || ...) catches any K_PQ_server vs K_PQ_client
divergence caused by either side's leniency. Per adversarial critic
analysis of 16 attack scenarios (rev-2026-0010), the lenient client does
NOT enable any active MITM attack because forging the server's signature
requires sk_host.

**Verified:** fnd-2026-0010 promoted to `verified_conclusion` with full
evidence chain.

### 3.3 GHA run 33304434203

One GHA run executed. Per-stimulus mutator results:
- control: handshake_aborted_sigfail (mutator_log - recv response EOF on subsequent packet)
- truncate_by_1: handshake_aborted_sigfail
- coeff0_q: handshake_aborted_sigfail
- coeff0_4095: harness_error (recv-upstream-sreply EOF)
- coeff255_4095: harness_error (recv-upstream-sreply EOF)
- cross_param_set: handshake_aborted_sigfail

**Root cause:** OpenSSH portable 10.5 defaults to strict-KEX ordering via
the kex-strict-s-v00@openssh.com extension (RFC 9142). The mutator does
NOT track the strict-KEX sequence number, so the client detects
out-of-order packets and aborts with handshake_aborted_sigfail. This
affects even the control case (no mutation), so it's a harness defect,
not a protocol verdict.

The sshd debug log confirms:
- sshd completes KEX (lenient on C_INIT per fnd-2026-0009)
- sshd sends NEWKEYS after KEX_REPLY
- sshd switches to encrypted mode (ssh_set_newkeys mode 1)

## 4. FIPS 203 spec analysis

Per FIPS 203 s7.3 (Algorithm 18 step 1), the decapsulation input check
is a hash check on the ciphertext vs the dk's embedded hash:
H(ct) vs dk[768k+32:768k+64].

This is the IND-CCA2 implicit rejection mechanism. The s7.2 modulus
check is on encapsulation keys (Algorithm 12 / Equation 7.1), not on
ciphertexts.

Therefore:
- Server-side (encaps): s7.2 mandate (per draft-ietf-sshm-mlkem-hybrid-kex-10 s2.1)
- Client-side (decaps): s7.3 mandate (no s2.1 explicit analogue in draft)

OpenSSH portable's protocol-layer placement of the s7.2 check is missing
on the server side (fnd-2026-0009) and structurally symmetric on the
client side (fnd-2026-0010), but the client-side leniency is on a
non-FIPS-203 check at the protocol layer (s7.3 is implemented inside
crypto_kem_mlkem768_dec, which OpenSSH portable delegates to).

## 5. Adversarial critic analysis (16 attack scenarios)

Per rev-2026-0010's systematic review:

| Scenario | Severity | Conclusion |
|----------|----------|------------|
| Pure tampered C_INIT, no MITM | IRRELEVANT | Cannot affect other parties |
| MITM tampers C_INIT, no host key | LOW | Signature check fails; same outcome as strict server |
| MITM tampers C_INIT + stolen host key | LOW | Even with host key, MITM cannot predict K_PQ_client (implicit-rejection random) |
| MITM with host key + X25519 tampering | LOW | X25519 point validation catches it independently |
| Server reaches NEWKEYS but client doesn't | LOW | SSH transport design prevents partial handshake exploitation |
| Wire-visible disconnect reason | IRRELEVANT | Same DISCONNECT_KEY_EXCHANGE_FAILED reason in both cases |
| Server log "incorrect signature" | LOW | Operator-side, not wire-visible |
| Repeated tampering DoS | LOW | Constant work; not new DoS vector |
| Tampered C_PK2 + rogue server | LOW | Game-over; leniency doesn't add vector |
| Server-side timing oracle | LOW | ML-KEM is constant-time |
| Strict server + lenient client (s7.3 missing) | IRRELEVANT in practice | No production SSH client is missing s7.3 |
| Post-quantum signature forgery | MEDIUM in future | If Ed25519 broken, s7.2 is secondary defense (but still compliance-only) |
| FIPS 140-3 compliance | MEDIUM | Real, but not security |
| Cleaner error reporting | LOW | Strict mode gives better diagnostics |
| Classical KEX precedent | LOW | Same leniency pattern deployed for ~20 years |
| Production deployment evidence | LOW | 24-month deployment pattern, external audit scrutiny |

**Overall verdict:** lenient client is **MODERATE** (compliance + future
defense-in-depth), NOT CRITICAL or MODERATE-exploitable.

## 7. Lessons learned

- The SSH exchange-hash signature verification is the actual load-bearing
  safety property for SSH KEX. FIPS 203 s7.2/s7.3 checks are correctness
  properties at the KEM primitive boundary, not protocol-level security
  boundaries.
- OpenSSH portable 10.5 defaults to strict-KEX ordering (RFC 9142 /
  kex-strict-s-v00@openssh.com extension). MITM mutators that don't
  track the strict-KEX sequence number will fail to relay correctly.
- FIPS 203 s7.2 (encaps key modulus check) is structurally different
  from s7.3 (decaps input hash check). Spec mandates apply to different
  sides of the KEM.
- Adversarial critic analysis of attack scenarios is essential for
  distinguishing "compliance gap" from "security vulnerability" claims.
