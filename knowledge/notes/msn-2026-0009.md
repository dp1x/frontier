# msn-2026-0009 - Cross-impl X-Wing + HPKE audit

## Mission goal

Extend msn-2026-0008 (CIRCL v1.6.5 X-Wing + HPKE byte-exact verification
against draft-08 KAT vectors) into a cross-implementation agreement matrix
between CIRCL (Go, turnkey X-Wing KEM + HPKE) and a pure-Python reference
implementation of draft-10 §5.3 (X-Wing Combiner) and RFC 9180 §5.1
(HPKE Base mode wrapping).

## Key technical decisions

### 1. Vendored CIRCL fork with an exported Components() accessor

CIRCL v1.6.5 ships `kem/xwing` with `Encapsulate`, `Decapsulate`,
`DeriveKeyPair` as the only public operations. The internal `(ss_M, ss_X,
ct_X, pk_X)` tuple fed to the X-Wing Combiner is never exposed, which makes
it impossible to independently re-run the Combiner on the same inputs that
CIRCL used internally.

Solution: vendor CIRCL's `kem/xwing/xwing.go` byte-for-byte (with the
`circl/internal/sha3` import swapped for `golang.org/x/crypto/sha3` because
internal/ packages are forbidden outside CIRCL) and add ONE additional
exported function `Components(pk, eseed) -> (ssm, ssx, ctx, pkx, ss, ct)`
that exposes the inner Combiner inputs to external auditors. Everything
else (combiner, EncapsulateTo, DecapsulateTo, deriveKeyPair, keygen
packing) is line-for-line identical to upstream CIRCL v1.6.5.

Verified: the vendored fork produces byte-exact identical KeyGenDerand
output to upstream CIRCL on the canonical test vector (the prior
mission's `vec-00000001` pk starts with `6f54098a0a0e6411...` in both
upstream and vendored forks).

### 2. Deterministic HPKE Base mode oracle

CIRCL's HPKE SetupS uses `rand.Reader` (cryptographic random) for the
ephemeral X25519 + ML-KEM eseed, making its HPKE output non-reproducible.
To enable byte-exact HPKE cross-comparison, the audit's Go oracle
implements HPKE Base mode wrapping manually using stdlib `crypto/aes`,
`crypto/hmac`, `crypto/sha256` directly, with the X-Wing KEM step using
`xwing.Encapsulate(pk, eseed)` where `eseed` is caller-controlled. This
makes the entire HPKE output deterministic.

The Go oracle's HPKE implementation was independently cross-checked
against the Python HPKE reference at the byte level on 10 random vectors.

### 3. pyca/cryptography 50.0.1 API limitations

pyca 50.0.1 exposes ML-KEM-768 via the OpenSSL EVP_PKEY interface but
does NOT expose `from_seed` keygen or `EncapsDerand`. This means:

  - byte-exact derandomized ML-KEM cross-comparison between pyca and CIRCL
    is INFEASIBLE in pyca 50.0.1.
  - pyca's ML-KEM round-trip correctness (encapsulate -> K, ct;
    decapsulate -> K'; K == K') is the best available primitive check.

When pyca exposes a `from_seed` API in a future release, the audit can
be extended to byte-exact ML-KEM cross-comparison. This is documented as
a follow-up.

### 4. Scope: only CIRCL exercised at the X-Wing KEM level

Of the five candidate implementations (CIRCL, Rust hpke, pyca, libhpke,
OpenSSL oqs-provider), only CIRCL ships a turnkey X-Wing KEM + HPKE
integration. The other four require building the X-Wing Combiner manually
on top of their primitives. The audit's scope was narrowed to:

  1. CIRCL turnkey (oracle)
  2. Pure-Python reference Combiner (cross-check)
  3. pyca primitives (X25519 cross-check + ML-KEM round-trip)

Extending the matrix to AWS-LC, libhpke, OpenSSL oqs-provider, and Rust
hpke is documented as a follow-up. These libraries require substantial
build setup (OpenSSL + oqs-provider is a known local-build challenge)
that exceeded this mission's time budget.

## What worked

- Building a small Go oracle that exposes CIRCL internals + implements
  deterministic HPKE took ~1 hour and worked immediately.
- The pure-Python X-Wing reference was ~30 lines and passed byte-exact
  on the first try, because draft-10 §5.3 is a 5-line algorithm.
- The Python HPKE reference was ~50 lines and passed byte-exact on the
  first try, because RFC 9180 §5.1 is well-specified.
- The mutation matrix confirmed the Combiner is input-sensitive at every
  tested position.

## What didn't work / known limitations

- draft-10 Appendix C has empty ct/ss fields (TODO placeholder) so there
  are no published draft-10 KAT vectors. The audit uses CIRCL's byte-level
  oracle as the reference, per hyp-2026-0010.
- pyca ML-KEM derandomized cross-comparison infeasible (API limit).
- Only CIRCL exercised at the X-Wing KEM level.
- 10 vectors is small for statistical purposes but adequate for
  deterministic byte-exact discriminators.

## Process findings (knowledge/process-findings candidates)

- Vendoring CIRCL with a single exported accessor is a clean way to get
  byte-level oracle access without forking upstream. This is a reusable
  pattern.
- A small Go subprocess oracle is preferable to importing a 3rd-party
  library in Python when byte-exact comparison is needed, because:
    - It isolates the trusted third-party code in a separate process.
    - It avoids FFI/ctypes complexity.
    - It enables precise version pinning.
  This pattern should be documented in workflows/.

- For protocols where the IETF draft has empty KAT vectors, the audit
  should fall back to a well-known reference implementation (CIRCL, in
  this case) as the byte-level oracle, and document the fallback
  explicitly in the spec artifact.

- The X-Wing Combiner is a 5-line SHA3-256 call with one 6-byte label.
  It's the kind of thing that gets right or wrong only in one place:
  the input order. The mutation matrix in this audit specifically
  tests order-sensitivity (swap_ssM_ssX, swap_ctX_pkX, drop_label).
  This is a useful pattern for any "single SHA3 call with labeled
  concatenation" combiner.

- HPKE Base mode's `HKDF-Expand-Label` structure (length-prefixed
  "HPKE-v1" || label, 2-byte L, 1-byte label length, 2-byte info
  length, info) is a common source of off-by-one errors. The audit
  confirms this works by byte-exact comparison; future HPKE audits
  should re-use the same oracle pattern.
