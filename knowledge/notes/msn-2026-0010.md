# msn-2026-0010 — SSH hybrid KEX protocol-layer FIPS 203 s7.2 audit

## 1. Mission summary

**Objective:** Determine whether OpenSSH portable's sshd enforces the
FIPS 203 s7.2 encapsulation-key modulus check on the C_PK2 portion of
SSH_MSGKEX_HYBRID_INIT before calling Encaps, as mandated by
draft-ietf-sshm-mlkem-hybrid-kex-10 s2.1 and
draft-ietf-sshm-ntruprime-ssh-06 s2.1.

**Result:** OpenSSH portable master HEAD commit 0ef0f5a8 sshd is
**length-only lenient** on the C_INIT portion of SSH_MSG_KEX_ECDH_INIT
(message 30) for both `mlkem768x25519-sha256` and
`sntrup761x25519-sha512` hybrid KEX cohorts.

**Verified:** fnd-2026-0009 promoted to `verified_conclusion` with
full evidence chain (experiment + observation + reproducer + verifier +
adversarial review).

## 3. Local constraint discovered

This Windows host has OpenSSH_for_Windows_9.5p2 + LibreSSL 3.8.2,
which does **NOT** support either `mlkem768x25519-sha256` or
`sntrup761x25519-sha512` KEX algorithms (`ssh -Q kex` shows only
classical algorithms). SCOUT-3's claim of "ssh.exe 9.5.6.1" was
wrong — actual version is 9.5p2 with LibreSSL.

Therefore the actual end-to-end test MUST run on GHA ubuntu-latest
where OpenSSH portable can be built from source with
USE_MLKEM768X25519=1.

### 4.4 Harness bug

The harness's `recvPacket` of the post-C_INIT response returns EOF
in all post-fix runs. The root cause is a residual timing/alignment
issue — the server's KEX_REPLY (31) is followed by NEWKEYS (21), and
the harness's recvPacket may be mis-aligned or the server's signature
verification fails before the response reaches the harness.

**This harness bug does NOT change the primary verdict** because the
server-side s2.1 enforcement question is determinable from:

1. Source code reading of `kexmlkem768x25519.c` (lines 117-130):
   only `sshbuf_len(client_blob) != need` check, no coefficient range
   check, before `crypto_kem_mlkem768_enc`.
2. Empirical sshd debug log: server reaches `SSH2_MSG_KEX_ECDH_INIT
   received` followed by `ssh_dispatch_run_fatal: incorrect signature`
   (downstream signature failure on garbage K_PQ).

The s2.1 mandate required SSH_DISCONNECT reason 3
(KEY_EXCHANGE_FAILED) before the KEM encapsulation step. The server
does NOT emit this — it proceeds to encapsulate.

## 5. Source-code audit (primary evidence)

### 5.1 ML-KEM-X25519 cohort

`openssh-portable/kexmlkem768x25519.c` (commit 0ef0f5a8), function
`kex_kem_mlkem768x25519_enc`, lines 117-130:

```c
/* client_blob contains both KEM and ECDH client pubkeys */
need = MLKEM768_PUBLICKEYBYTES + CURVE25519_SIZE;
if (sshbuf_len(client_blob) != need) {
    r = SSH_ERR_SIGNATURE_INVALID;
    goto out;
}
client_pub = sshbuf_ptr(client_blob);
/* ... no 12-bit coefficient range check ... */
if (crypto_kem_mlkem768_enc(ct, shared_secret, client_pub) != 0) {
    r = SSH_ERR_INTERNAL_ERROR;
    goto out;
}
```

The only check on `client_blob` before `crypto_kem_mlkem768_enc` is the
length check. The 12-bit coefficient range check required by FIPS 203
s7.2 (and mandated by draft-ietf-sshm-mlkem-hybrid-kex-10 s2.1) is
**not implemented** at the protocol layer.

### 5.2 Sntruprime-X25519 cohort

`openssh-portable/kexsntrup761x25519.c` (analog structure) follows the
same length-only pattern.

## 10. Lessons learned

- SSH version banner exchange (RFC 4253 s4.2) is mandatory before
  binary packet protocol. Harness without banner produces
  "kex_exchange_identification: banner line contains invalid
  characters".
- Name-list encoding uses a single outer uint32 length prefix
  (RFC 4251 s5), not per-name length prefixes.
- bufio.Reader is needed for proper banner/packet boundary alignment.
- OpenSSH maps hybrid KEX to standard SSH_MSG_KEX_ECDH_INIT (30) /
  SSH_MSG_KEX_ECDH_REPLY (31) — NOT to the draft's separate
  SSH_MSG_KEX_HYBRID_INIT.
- Source-code reading of the relevant `kex_kem_*_enc()` function
  is the authoritative oracle for "what the server does before
  Encaps". Empirical sshd log confirms the server reaches the Encaps
  step rather than rejecting with SSH_MSG_DISCONNECT.
- Harness bugs that prevent capturing the post-Encaps server response
  (KEX_REPLY) do NOT invalidate the primary verdict when the
  verdict is determinable from source-code + server's KEXINIT-reach
  observation.
