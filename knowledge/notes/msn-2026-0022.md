# msn-2026-0022 — X.509 pathLenConstraint conformance

## The question, and why it was not answered the obvious way

The inherited lead was a table on a public site: C2SP x509-limbo reports that
`pathlen::self-issued-certs-pathlen` is expected-SUCCESS and that several
implementations fail it. The obvious conclusion is "several implementations have
a pathLen bug".

That conclusion was not assumed. It was treated as a lead, and the mission was
scoped to determine independently what is actually true.

## What the RFC actually says

The decisive clause had never been cited by any inherited source — not by
x509-limbo, not by the implementation folklore, not by Frontier's own reports:

> RFC 5280 §6.1: "This section presents the algorithm in four basic steps:
> (1) initialization, (2) basic certificate processing, (3) preparation for the
> next certificate, and (4) wrap-up. Steps (1) and (4) are performed exactly
> once. Step (2) is performed for all certificates in the path. **Step (3) is
> performed for all certificates in the path except the final certificate.**"

Step (3) *is* §6.1.4, and §6.1.4 is where the path-length decrement and the
pathLenConstraint clamp live. So the final certificate is excluded from
path-length processing entirely. That single sentence is what makes the counting
rule derivable, and it is four paragraphs away from the loop body that everyone
had been reading.

Three independent derivations (SA-1, SA-5, OR-1) converged on the same
acceptance predicate. SA-4 supplied a structural fact the agreement alone does
not: **"intermediate certificate" is never defined in RFC 5280.** It occurs
exactly once, inside the §4.2.1.9 parenthetical. The counting rule rests on a
*positional* reading of §6.1, not on a defined term.

## What the measurements show

| | rustls-webpki | certvalidator | RFC 5280 oracle |
|---|---|---|---|
| c10 non-self-issued twin | REJECT | REJECT | REJECT |
| c11 self-issued | **REJECT** | **ACCEPT** | ACCEPT |
| c12 non-self-issued twin | REJECT | REJECT | REJECT |
| c13 self-issued (constrained) | REJECT | REJECT | ACCEPT |
| c17 constrained trust anchor | REJECT | REJECT | ACCEPT |
| c20 slot sensitivity (pl=2) | ACCEPT | ACCEPT | ACCEPT |

Two lineages, genuinely independent: certvalidator is a pure-Python
transcription of §6.1 with no OpenSSL delegation; the cryptography path is
compiled Rust vendoring rustls-webpki. They do **not** fail together on c11, so
the webpki result is attributable to that core rather than to a shared
misreading.

The trust-anchor divergence (c17) **is** shared by both, and is a cleaner
finding: neither needs the self-issued subtlety, the reason class is path
length, and certvalidator's own source comment says the anchor is not part of
the path while its code seeds the budget from the anchor's pathLenConstraint.

## What this mission cost, honestly

The instrument was wrong three times, and each time the **corpus** caught it,
not review:

1. The oracle applied §6.1.4 to the final certificate, rejecting legal
   pathlen:0 penultimate chains. Found by re-reading §6.1, not by a test.
2. A second off-by-one rejected `pathLen 1 → 2` increases.
3. A per-position check was computed and then never gated on, so every case
   accepted.

All three wrong versions are preserved in `oracle.py` with the reason each was
wrong, because the wrong version is the natural one to write.

Two harness confounders were found the same way, each of which would have made
the entire matrix uninterpretable while still producing plausible FAIL/PASS
output: a missing subjectAltName (every case failed identically at name
matching) and a spurious AuthorityKeyIdentifier on the root. Neither is visible
in a pass/fail summary.

## Status

`fnd-2026-0016` is a **candidate**, not a promoted finding. It has no
independent review yet, and its scope is deliberately one measured core. No
security impact is claimed: in every observed case the implementation is
*stricter* than the RFC, which is an interoperability concern, not a trust
bypass.

## The methodological lesson worth carrying

The brief said the Frontier corpus exists "to ensure that a pathLen observation
cannot be dismissed because the generated certificate also violated an unrelated
rule." That is exactly what happened — twice — and neither was visible without
reason classification. The single most valuable piece of code in this mission
is not the oracle; it is the reason classifier.
