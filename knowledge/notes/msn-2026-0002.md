**The headline refutation is a real, reproducible cross-API variance in
OpenSSL 3.5.7**: `d2i_PUBKEY` accepts over-length and cross-param-set key
bodies that `EVP_PKEY_new_raw_public_key_ex` correctly rejects, and
proceeds to a successful encap. The 6 vectors are also rejected by .NET
(both Windows CNG and Linux OpenSSL-backed).

The 6 killing vectors are reproducible by anyone running
`crypto/mlkem-input-checks/harnesses/openssl_invar_runner.c` against the
committed `stimuli.tsv` (199-vector manifest). The harness uses hard-coded
22-byte RFC 9480 algorithm-OID prefixes and appends the raw test bytes
verbatim, so the malformed body is the test stimulus itself, not a
harness artifact.

## FIPS fix committed

Two changes, both pushed to `main` as commit `88b10af`:

1. **Harness (`openssl_fips_runner.c`, `openssl_invar_runner.c`):** defer
   `ERR_clear_error()` until after the error has been captured with
   `ERR_get_error()`. The pre-fix code cleared the error queue before
   peeking it, producing the literal `"no-fips-module"` string for every
   failure mode (env-var missing, `OSSL_LIB_CTX_load_config` failure,
   `dlopen` failure, provider not found). Capture up to 6 errors with
   `lib:reason` formatting; distinguish the silent no-env case from
   "no-fips-module".

2. **Workflow (`.github/workflows/mlkem-invariance.yml`):**
   - `Configure --libdir=lib64` (close `lib`/`lib64` ambiguity)
   - `set -euxo pipefail` (fail loudly on any silent step)
   - New "Verify FIPS module integrity at install path" pre-step that
     runs `fipsinstall -verify` and `openssl list -providers` and uploads
     both logs as artifacts
   - `LD_LIBRARY_PATH` exported to `$GITHUB_ENV` so subprocesses use
     prefix libs
   - Runner stderr redirected to `openssl_fips_runner.stderr` and
     uploaded as artifact so the per-stage trace survives failed runs
   - `openssl list -providers` in the build step exercises the same
     loader path the harness uses, with the same env vars
