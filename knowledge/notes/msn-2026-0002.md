## This session (2026-08-29): fnd-2026-0002 PROMOTED to verified_conclusion

The session executed 5 parallel work tracks, of which fnd-2026-0002
verification was the headline:

1. **Pushed** the 9 commits to origin/main (GHA run 33223536290
   triggered, all 6 jobs passed).

2. **Downloaded** the GHA artifacts (openssl_fips_report, openssl_invar_report,
   oqs_auto_report, oqs_ref_report, dotnet_invar_*) and committed them
   as durable evidence. The 6 divergent vectors in fnd-2026-0002 are
   reproduced in openssl_invar_report.tsv: 3 len-plus-1 + 3 cross-set-*
   rejected by raw/default and accepted by spki/default with encap-accepted.

3. **FIPS diagnosis**: GHA run 33223536290 confirmed fipsinstall -verify
   PASSED (module integrity values generated) but the FIPS provider
   fails the post-integrity self-test on the runner
   ('Provider routines: missing config data|Provider routines:
   fips module entering error state|Provider routines: self
   test post failure|common libcrypto routines: init fail' on
   the invar run; 'system library|common libcrypto routines:
   provider section error|configuration file routines: module
   initialization error' on the fips-only run).

   Root cause: OpenSSL 3.5.7's FIPS module does not include ML-KEM
   in its FIPS boundary. The FIPS cell is structurally unanswerable
   for ML-KEM, not a transient infrastructure issue. The FIPS
   dimension of hyp-2026-0002 is preserved as INCONCLUSIVE-AFTER-BUDGET.

4. **Source-level adversarial review** (subagent 01a04aeb-8994,
   474s/27 tool calls): traced d2i_PUBKEY -> x509_pubkey_ex_d2i_ex
   -> OSSL_DECODER -> ossl_ml_kem_d2i_PUBKEY path through OpenSSL
   3.5.7 source. Verdict: mechanism SUPPORTED with magnitude
   CORRECTION (1-byte over-shoot -> 33-byte over-shoot for
   len-plus-1, up to 800-byte over-shoot for cross-set). The
   correction is because the harness uses test_ek of length 833
   (body + 33 derived bytes), not 801 (body + 1). All file:line
   citations in obs-2026-0022.

5. **Independent reproducer** (subagent 01a04aeb-8996, 2209s/116
   tool calls): built 5 fresh, self-contained C programs (no code
   imported from openssl_invar_runner.c) and ran them on OpenSSL
   3.6.3 MSYS2 local. Direct observations:
   - len-plus-1 ML-KEM-512: parser-consumed=822 of 823
   - cross-set-1024-as-768: parser-consumed=1206 of 1590
   - canonical 512: positive control passes
   - alg_check: re-encoded SPKI is canonical 822 bytes, OID
     matches prefix's param set, keymgmt params (bits=512,
     security_bits=128, size=768) match OID not raw body length
   - cross-version: OpenSSL 3.5.7 (GHA) and 3.6.3 (local) both
     exhibit the same mechanism

6. **fnd-2026-0002 PROMOTED** to verified_conclusion. The candidate
   finding's mechanism is now end-to-end source-verified (with
   file:line citations) + independently reproduced on a different
   OpenSSL version (3.6.3 vs 3.5.7) + cross-stack correlated against
   4 other stacks (all reject).
