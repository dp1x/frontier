# msn-2026-0002 — active notes

## Question

Do FIPS 203 §7.2 encapsulation-key check outcomes stay invariant when the *same* library is exercised through different internal paths?

Hypothesis [[hyp-2026-0002]] predicts **yes** — verdicts identical across:
- OpenSSL raw-bytes vs DER/SPKI import, default vs FIPS provider
- liboqs runtime-selected mlkem-native backend vs forced-ref
- .NET Windows CNG backing vs Linux OpenSSL backing

The hypothesis was left `inconclusive` after [[msn-2026-0001]] because only one path per library was executed (OpenSSL raw/import default, liboqs avx2=1 auto-selected, .NET CNG only).

## Killing observations

- Any input accepted by one path while the equivalent path rejects it.
- For OpenSSL: raw accepts / SPKI rejects (or vice versa) for same `ek` bytes.
- For FIPS: default provider accepts / FIPS rejects.
- For liboqs: forced-ref verdict table != auto-selected table (Compare-Object non-empty).
- For .NET: CNG verdicts != Linux OpenSSL verdicts.

If no divergence is observed across the full executed matrix, [[hyp-2026-0002]] resolves to **supported** (invariance holds where measured). Any divergence resolves to **rejected** and becomes a classified finding (format/provider/backing-dependent validation). Partial execution leaves it `inconclusive-with-reason` with explicit blocked cells.
