# Deep-research request: is pycose's COSE protected-header key ordering already a known issue, and is it a usage error on our side?

## Why this request exists

We measured a byte-level divergence between pycose 1.1.0 and a from-scratch
reference oracle for COSE_Sign1 protected headers. Before we report anything to
the pycose maintainers we need two things we cannot obtain locally: **whether this
is already known**, and **whether pycose has a supported canonical mode we simply
failed to turn on**. Do not assert novelty. Report only what exists.

## Self-contained context

System under test: **pycose 1.1.0**, Python 3.11.15, CBOR backend **cbor2 6.1.4**.
All measurements are byte-exact and reproducible.

The requirement at issue: **RFC 9052 section 9** (COSE message structures) requires
the deterministic encoding of **RFC 8949 section 4.2.1** (bytewise lexicographic
order of the deterministic encodings of map keys) for the protected header map.
The protected bucket is carried inside Sig_structure as a bstr, byte-for-byte, so
two implementations that order the same logical map differently produce different
Sig_structure bytes.

### Reproducer A - tstr-only protected map

Logical protected map (no `alg` in the protected bucket):

```
{"a": 1, "aa": 2, "b": 3, "ab": 4, "z": 5}
```

Sig_structure per RFC 9052 section 4.4:
`["Signature1", body_protected, external_aad, payload]`, with
external_aad = h'' and payload = h'70'.

| | protected bstr hex | decoded key order |
|---|---|---|
| RFC 8949 section 4.2.1 (required) | `a5616101616203617a056261610262616204` | a, b, z, aa, ab |
| pycose 1.1.0 (observed) | `a56161016261610261620362616204617a05` | a, aa, b, ab, z |

Full Sig_structure as actually emitted:

- RFC 8949 section 4.2.1 conformant:
  `846a5369676e61747572653152a5616101616203617a056261610262616204404170`
- pycose 1.1.0:
  `846a5369676e61747572653152a56161016261610261620362616204617a05404170`

Note both protected buckets are **18 bytes** (`0x52`) - the difference is purely
key order, not length. The pycose order a, aa, b, ab, z is exactly the insertion
order of the dict as constructed.

### Reproducer B - int-key map (this is the case that rules out a tstr-only scope)

Supply the same key/value pairs in descending insertion order:

```
{4: b'y', 3: 50}
```

| | protected hex | key order |
|---|---|---|
| RFC 8949 section 4.2.1 (required) | `a2031832044179` | 3, 4 |
| pycose 1.1.0 (observed) | `a2044179031832` | 4, 3 (insertion order, unsorted) |

So the behaviour is **not** confined to text-string keys. When the input happened
to be supplied already sorted, pycose matched by coincidence.

### Minimal pycose snippet we used

```python
from pycose.messages import Sign1Message
from pycose.headers import Algorithm
from pycose.algorithms import Es256

msg = Sign1Message(phdr={Algorithm: Es256}, payload=b"p")
msg._create_sig_structure()   # element 1 is the protected bstr
```

We fed the protected map through pycose's header dict and read the resulting
Sig_structure. We did **not** find or enable any canonical-ordering option. That
absence is itself a question for you (Q2).

### What we are NOT claiming

- We are not claiming this is a security vulnerability.
- We are not claiming it is previously unreported. We have not checked.
- We are not claiming our measurement is the only correct reading of the spec.
