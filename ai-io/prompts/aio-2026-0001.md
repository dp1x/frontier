# Deep-research request: prior art on ML-KEM encapsulation-key validation behavior

## Self-contained context

FIPS 203 (final, 2024-08-13) §7.2 requires an "encapsulation key check" before
ML-KEM.Encaps runs on an externally supplied key: (1) type check — length must
equal 384k+32 bytes; (2) modulus check — ByteEncode12(ByteDecode12(ek[0:384k]))
must equal ek[0:384k] byte-for-byte, which fails exactly when some decoded
coefficient is ≥ q = 3329 (12-bit segments can hold up to 4095). The standard
allows the check to be performed elsewhere or amortized ("need not be performed
by the encapsulating party, nor with every execution"), deferring to SP 800-227
(final, 2025-09-18) §3.2's three assurance cases.

Our own pinned static analysis (2026-08-24): PQClean master 0586a824 performs NO
ek validation on the encaps path; liboqs 0.16.0 (vendored mlkem-native v1.2.0)
performs the modulus check unconditionally inside Encaps; OpenSSL 3.5.7 enforces
both checks only at key import. Public corpora: NIST ACVP `encapsulationKeyCheck`
function class; C2SP Wycheproof ML-KEM `ModulusOverflow` encaps vectors.
