# Deep-research request: who checks the ML-KEM encapsulation key in deployed protocols?

## Self-contained context

FIPS 203 §7.2 mandates an encapsulation-key check (length 384k+32; modulus
roundtrip ByteEncode12(ByteDecode12(ek[0:384k])) == ek[0:384k], q = 3329) but
explicitly allows the check to live elsewhere than the encapsulating module
("assurance ... acquired through other means", SP 800-227 §3.2). Our static
analysis shows real libraries diverge: OpenSSL enforces at import;
liboqs/mlkem-native inside Encaps; PQClean not at all.

The open question: in the protocols that actually carry ML-KEM public keys
across the wire today, which layer is SPECIFIED or IMPLEMENTED to perform the
§7.2 check on the received peer key?

## Questions to resolve

1. For TLS 1.3 X25519MLKEM768 (and related hybrid groups in RFC drafts /
   final RFCs, e.g., draft-ietf-tls-ecdhe-mlkem and successors): do the protocol
   documents require the client to validate the server's ML-KEM public key
   before encapsulation? Quote normative text.
2. For HPKE with post-quantum KEMs (draft-ietf-hpke-pq specs and ML-KEM
   integrations): same question for the sender side.
3. For IKEv2 hybrid PQ key exchange (RFC 9370 series) and any SSH/post-quantum
   hybrids carrying ML-KEM public keys: same question.
4. Implementation reality: what do major stacks (Go crypto/tls, BoringSSL/
   Chrome, OpenSSL-based servers, rustls, AWS-LC/s2n) actually DO when a peer
   sends a non-canonical ML-KEM public key in these handshakes — cite source
   files, issue threads, or maintainer statements.
5. Is there documented interoperability breakage or security discussion about
   non-canonical keys at the PROTOCOL layer (not library unit level)?
