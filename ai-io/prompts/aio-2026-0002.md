# Deep-research request: CMVP/FIPS 140-3 treatment of ML-KEM §7.2 check placement

## Self-contained context

FIPS 203 §7.2 defines the encapsulation-key check (type: length == 384k+32;
modulus: ByteEncode12∘ByteDecode12 roundtrip on ek[0:384k], q = 3329) and states:
"ML-KEM.Encaps shall not be run with an encapsulation key that has not been
checked as above. However, checking ... need not be performed by the
encapsulating party, nor with every execution ... assurance ... acquired through
other means (see SP 800-227)." SP 800-227 (final 2025-09-18) §3.2 lists three
assurance cases: internal generation + tamper-evident storage; check-once +
tamper-evident storage; TTP-import with assurance. NIST ACVP already contains a
dedicated ML-KEM `encapsulationKeyCheck` function class whose `ValuesTooLarge`
cases must be rejected.

The open interpretive question for our research: whether a cryptographic module
that exposes "import raw ML-KEM public key, then Encaps" WITHOUT performing the
§7.2 checks anywhere in that path can be FIPS 140-3 validated, given that the
application layer could theoretically provide SP 800-227-style assurance.

## Questions to resolve

1. In actual CMVP validation practice (Implementation Guidance, lab notes,
   validation certificates for ML-KEM-capable modules), is the §7.2 check treated
   as a testable module requirement, an application responsibility, or both?

2. Are there validated modules (any vendor) whose security policy explicitly

   placement? Any published CMVP dispute resolutions touching §7?
4. What do the ACVP `encapsulationKeyCheck` conformance requirements imply about
